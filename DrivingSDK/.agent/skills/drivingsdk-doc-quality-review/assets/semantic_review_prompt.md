# 语义复核 / 汇总把关 Prompt（semantic 道 + 汇总环节）

本道由 LLM 承担两件事：

1. **检测**机械道查不出的问题：语法/任意错别字、表述歧义、描述与代码是否一致、逻辑矛盾、过期信息；
2. **汇总把关**：对前面 structure/format/terminology/grammar 各道产出的候选**过一遍**，
   结合下方「领域保护术语」剔除误报、补充遗漏，再合成最终清单。

> 各机械道照常全量检测（不前置压制），保护术语在**本汇总环节**交给 LLM 作判断依据。

## 领域保护术语（必读，先加载）

先读取 `assets/domain_terms.txt`（品牌名 + 昇腾/NPU/自动驾驶/大模型领域术语，如
`昇腾`、`算子`、`融合算子`、`稀疏卷积`、`体素化`、`点云`、`CANN`、`mx_driving`、`BEVFormer` 等）。**这些是正确写法**：

- **绝不**把它们标为错别字/拼写错误/术语错误；
- 复核机械候选时，**若某条把保护术语误判为错误，直接判为误报并剔除**；
- 它们也是上下文：理解文档在讲什么，再判断描述与代码是否一致。

两种执行方式，**同一套判定标准与产出格式**：

- **方式 A（默认，推荐）：in-agent**——当本 skill 由代码助手（如 Claude Code）运行时，
  **助手自身就是 LLM**，直接按下面流程读文档、`grep`/`read` 仓库代码做判断，
  **无需任何外部 API/密钥**。代码一致性类问题尤其依赖这一点（能真的去查代码）。
- **方式 B：headless/CI**——无代码助手在环时，用 `scripts/llm_review.py` 调外部 OpenAI 兼容接口
  （用户提供 `--api-base/--model/--api-key-env`，默认 dry-run）。它只看文档文本，**无法核对代码**，
  故代码一致性类判断弱于方式 A。

## 判定流程（逐文件）

1. **通读**该文档，标记可疑句。
2. **语法 / 错别字**：病句、成分残缺、语序错乱、指代不清、任意错别字（不限于混淆集）。
3. **表述**：歧义、冗余、自相矛盾、同一概念前后不一致。
4. **描述与代码一致性（最重要，必须核对，别臆断）**：
   - 文档提到的**接口名 / 参数 / 路径 / 文件名 / 默认值 / 环境变量**，用 `grep`/`read` 到仓库里核对是否存在、是否一致。
     例：API 文档写某算子 `mx_driving.xxx`，去 `grep -rn "xxx" mx_driving/ model_examples/` 确认接口名、入参与实现一致；
     example 的启动命令/脚本名去对应 `model_examples/<模型>/` 下核对是否存在。
   - 文档引用的**脚本 / model_examples 路径**是否真实存在。
   - **版本号 / 配套表**是否与 `docs/zh/version/versions.md`、`release_note`、`installation` 自洽。
5. **过期信息**：已删除的脚本、改名的模块、失效的链接锚点。
6. **判定纪律**：拿不准 → 去查代码；查不到定论 → 标 `severity=info` 且 suggestion 注明「待人工确认」；
   只产出**能给出具体改法**的问题，附依据（如「代码 xxx.py:NN 实际默认值为 0.0001」）。

## 产出格式（每条，便于并入 issue）

```text
文件:行号 | 类型(语法/错别字/语义/一致性/过期) | 级别(error/warning/info) | 原文片段 | 修改建议(+依据)
```

- 级别：与代码/链路不符、坏命令 = error；明显语病/错别字 = warning；优化/待确认 = info。
- 与 structure/terminology/format 道的发现**合并**后统一进 issue（结构逐条、术语聚合、格式汇总）。
